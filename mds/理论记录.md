# 理论记录 — 2026-08-13

## 1. 编辑策略统一：经验参考生成

### 旧策略
- `rewrite_param`：字符串替换（如 `'sensors'` → `'cameras'`），0 Token，泛化极差
- `rewrite_content`：LLM 带上下文重写，~200 Token
- `regenerate`：LLM 从零重新生成，~500 Token

### 新策略（统一为 `reference_generate`）
**核心原则：提供成功执行的 SQL 作为参考，让 LLM 在此基础上生成新 SQL，而非从零生成。**

```
旧轨迹 SQL: "SELECT COUNT(*) FROM tb_device WHERE online_status = 'online'"
新查询: "查前天的摄像头在线率"
LLM 任务: 参考上面的 SQL，生成新查询对应的 SQL
```

**优点：**
- 明确告诉 LLM"这是成功经验"，LLM 更倾向于沿用相同结构，减少幻想
- 不需要做参数提取，保留泛化能力
- 出错概率更低，因为有具体参考

### 结论
- `reference_generate` ≈ 参数编辑 + 重新生成 的合并升级
- 参数编辑（日期替换）本质是"成功经验+小改动"——不是省 Token，而是减少犯错
- 不要用规则做参数替换，泛化太差；让 LLM 在模板约束下生成

## 2. TaaS（Trajectory-as-a-Skill）

### 定义
将历史执行轨迹（Trajectory）抽象为可复用的技能（Skill），实现"经验即服务"。

### 与业界 Skill 的本质区别
> Skill 和 TaaS 是同一个问题的两个极端：
> - **Skill（Function Calling）**：开发者预定义的确定性功能模块，固定输入输出 schema，泛化能力弱但执行确定
> - **TaaS（Trajectory-as-a-Skill）**：从执行中自动积累的轨迹，通过语义检索 + LLM 编辑适配新查询，泛化能力强但执行带概率性

### TaaS vs Skill 优缺点对比

| 维度 | TaaS（轨迹检索） | 业界 Skill（Function Calling） |
|------|----------------|------------------------------|
| 定义方式 | 自动积累，从执行中学习 | 开发者手动定义，固定 schema |
| 粒度 | 精细（节点级，可编辑） | 粗粒度（整个函数） |
| 泛化能力 | 强（语义检索 + LLM 编辑） | 弱（只能处理预定义输入） |
| 冷启动 | 自动从 0 积累 | 需要预先写好所有 Skill |
| 维护成本 | 低（自动入库，自动衰减） | 高（新增需求必须写新 Skill） |
| 确定性 | 弱（LLM 编辑有概率性） | 强（固定逻辑，确定执行） |
| Token 效率 | 高（一级 0T，二级 ~200T） | 中（每次要 LLM 选 Skill） |
| 可解释性 | 高（轨迹可回放、可审查） | 中（黑盒函数调用） |
| 领域迁移 | 容易（新领域自动积累） | 困难（需要重写所有 Skill） |

### TaaS 与 Skill 的关系
- **TaaS 是 Skill 的超集，Skill 是 TaaS 的确定性子集**
- 轨迹中的 `tool` 类型节点 = 确定性 Skill 调用（执行 100% 确定）
- 轨迹中的 `llm_generate` 类型节点 = 概率性 Skill 调用（LLM 生成，带概率性）
- 轨迹整体 = 一个"动态 Skill"——能通过语义检索被发现，通过 LLM 编辑适配变体

### 设计原则
- TaaS 是上层框架，Skill 是底层原子
- 一条轨迹 = 多个 Skill 节点 + 多个 LLM 节点的有序组合
- 轨迹中的 Skill 节点提供确定性，LLM 节点提供泛化能力
- 长期目标：高频轨迹模式自动提炼为永久 Skill，从"概率性经验"升级为"确定性能力"

## 3. 自动 Skill 提炼

### 正反馈循环
```
轨迹自动积累 → 高频模式自动提炼为细粒度 Skill → Skill 提供确定性执行 → 更多轨迹积累 → 更细的 Skill 提炼
```

### 当前 Skill 粒度问题
- `execute_sql` 太粗——它只是"执行任意 SQL"，不知道具体查什么
- 需要的细粒度：`query_sensor_online_rate(device_type, date)`、`query_alarm_count(period, region)`
- 细粒度 Skill 从轨迹中自动提炼，而非开发者手动定义

### 提炼规则
1. 同一条轨迹模式出现 N 次（默认 3 次）→ 自动提炼为一个 Skill
2. 提炼时分析轨迹中 LLM 生成的节点，提取可变参数（如 `device_type`、`date`）
3. 生成的 Skill 注册到 Skill 注册表，可供后续链路直接调用
4. 提炼后的 Skill 使用者优先使用（0 Token，100% 确定），而非 LLM 重新生成

### Skill 在 TaaS 中的角色
- **确定性锚点**：轨迹中可编辑的节点，优先用 Skill 调用（0 Token，确定）
- **编辑失败兜底**：LLM reference_generate 失败时，回退到 Skill 的原始调用
- **执行引擎**：所有 tool 类型节点本身就是 Skill 调用
- **自动提炼目标**：高频轨迹模式 → 永久 Skill

## 4. 编辑优先级

```
编辑节点时：
  1. 先查节点是否关联了细粒度 Skill
  2. 有 Skill 且参数可映射 → 直接 Skill 调用（0 Token，100% 确定）
  3. 无 Skill 或参数映射失败 → LLM reference_generate（~200 Token，概率）
  4. reference_generate 失败 → 保留原节点（兜底）
```

## 5. 通用泛化能力

### 项目不依赖特定领域
- 即使查询涉及不同业务（传感器 vs 摄像头），都可抽象为执行轨迹的节点
- SQL 相关、业务特定的工具 Skill，在用户自己的业务下自然会写好类似节点
- 通用泛化不差——所有工作流都可分解为"工具节点 + LLM 节点"的序列

## 6. TRIAGE vs TaaS 命名定位

### 不能相互替换，它们在不同层面

| | TRIAGE | TaaS |
|--|--------|------|
| 层面 | 项目/架构名 | 理论/概念名 |
| 回答什么 | "怎么做" | "是什么" |
| 范围 | 三级路由 + 检索 + 编辑 + 冷启动 + 实验 | 轨迹即 Skill 这一核心思想 |
| 论文中 | 出现在标题、方法、实验 | 出现在核心概念、相关工作对比 |

### 比喻
- TRIAGE = **Transformer**（架构名）
- TaaS = **Attention**（核心概念）
- 不会用"Attention"代替"Transformer"，但会说"Transformer 的核心是 Attention"

### 论文和项目中的定位

```
论文标题：TRIAGE: Three-level Routing and Intelligent Agent Guidance...
          ↓
核心概念：TaaS（Trajectory-as-a-Skill）—— 轨迹即 Skill
          ↓
架构实现：三级路由 + 语义检索 + 经验参考生成 + 自动 Skill 提炼
          ↓
项目名：TRIAGE（GitHub 仓库名）
```

**TaaS 是 TRIAGE 的理论核心，TRIAGE 是 TaaS 的工程实现。**
